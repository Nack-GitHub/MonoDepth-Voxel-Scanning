## 6.1 ทำไม per_scene แพ้ oracle 4.5 เท่า: scale ของโมเดลเปลี่ยนตาม "สิ่งที่อยู่ในเฟรม" ไม่ใช่ตามเวลา

โมเดล affine-invariant สัญญาว่า `disparity ≈ a·(1/depth) + b` โดย `(a, b)` ขึ้นกับภาพ ถ้า `(a, b)` คงที่ทั้ง scan calibration ครั้งเดียว (`per_scene`) จะเท่ากับ oracle
เราวัดว่ามันคงที่แค่ไหนโดย fit `(s, t)` ใหม่ทุกเฟรมที่ 5 (471 เฟรมจาก 6 ฉาก) — **ตาราง 6.1** (DA-v2 Large, ค่าต่อฉาก):

| | ช่วงข้ามฉาก | ความหมาย |
|---|---|---|
| `s` p95 / p5 ภายในฉากเดียว | **2.6–4.9×** | เฟรม 90 % กลางของ scan เดียวกันต้องการ scale ต่างกันได้ถึง 3–5 เท่า |
| `s` p75 / p25 | 1.47–1.56 | แม้ครึ่งกลางของเฟรมยังแกว่ง ±25 % |
| corr(`s`, เวลา) | −0.33 … +0.30 (สลับเครื่องหมายข้ามฉาก) | **ไม่ใช่ drift สะสม** — ไม่มีทิศทาง |
| corr(`s`, median depth ของเฟรม) | **−0.27 … −0.75 (ลบทุกฉาก)** | เฟรมที่มองใกล้ได้ `s` ต่างจากเฟรมที่มองห้อง — ขึ้นกับมุมมอง |
| AbsRel oracle → per_scene | 0.032 → 0.239 (**7.5×**) | ในสเปซ 2D ก่อน fuse ราคาของ scale เดียวคือ 7× |
| per_scene ตัด close-up (< 1 m) ออก | 0.152 (ยัง 5× oracle) | close-up ทำให้แย่ลง แต่ไม่ใช่สาเหตุเดียว |
| scale-only ต่อเฟรมในสเปซ depth | 0.289 ≈ per_scene | shift ใน disparity จำเป็นทุกฉาก (ยืนยัน ADR-010 ทั่วไป) |

สามข้อสรุปที่ตามมา:

1. **ไม่มีจำนวน fit frame ใดช่วย per_scene** — `(S, T)` ที่ fit จาก 10 เฟรมกระจาย อยู่ห่าง median ของ oracle ไม่เกิน ±13 % ใน 5 จาก 6 ฉาก (0.87–1.17×; ยกเว้น 47333774 = 0.67×)
   ปัญหาคือ median เองใช้กับเฟรมส่วนใหญ่ไม่ได้ ไม่ใช่ว่าประมาณ median ผิด
2. **error ต่อเฟรม 7.5× กลายเป็น error 3D 4.5×** ไม่ใช่เพราะ TSDF ช่วยเฉลี่ย แต่เพราะ error กระจุกที่เฟรมส่วนน้อย: เฟรมที่ per_scene AbsRel > 1 (วางผิดที่ ≥ 2 เท่า)
   คือภาพก้มถ่ายของบนโต๊ะ/พื้นที่ 0.5–0.8 m และผนัง/ตู้เรียบเต็มเฟรม (`figures/42444474_failure_frames.png`) — เฟรมพวกนี้ไม่มี cue บอกขนาด โมเดลจึงเดา disparity ใน "สเกลห้อง"
   พอคูณด้วย `(S, T)` ของห้อง โต๊ะที่ 0.5 m ไปโผล่ที่ 1.5–2 m เป็นผิวปลอมกลางห้อง = ก้อนแดงใน grid รูป 5.1 แถว per_scene ทุกฉาก
3. **ผลนี้ทั่วไป ไม่ใช่สมบัติของฉากพัฒนา** — 47429736 (ห้องนอน+ตู้) มี close-up 53/101 เฟรมแต่ per_scene = 0.197 เท่ากับฉากที่มี close-up 3/93 (45261556: 0.172)
   และ 5 ฉากที่ pipeline ไม่เคยเห็นให้ Chamfer per_scene 19.9–26.0 cm ครอบ 42444474 (24.1) พอดี

**นัยต่อระบบ:** สมมติฐาน "scale เดียวต่อฉาก" ผิดสำหรับโมเดลตระกูลนี้บนวิดีโอห้องจริง ทางที่เหลือมีสอง: (ก) ข้อมูล metric *ต่อเฟรม* — จุด feature 3D จาก VIO ซึ่ง ARKit/ARCore
ให้มาพร้อม pose อยู่แล้ว (`sparse_points` aligner, §8.3) หรือ (ข) ทิ้ง/ลด weight เฟรมที่ไม่มี cue ก่อน fuse — (ข) ถูกกว่าแต่ตัด close-up ออกยังเหลือ 5× oracle จึงเป็นได้แค่ตัวเสริมของ (ก) — Exp1 ยืนยัน (ก): จุด 200 จุดต่อเฟรมพาแถวมาที่ 6.0 cm ห่าง oracle 0.6 cm ลำดับต่อฉากเหมือน oracle และการ fit ต่อเฟรมไม่ต้องใช้ประวัติ เฟรมที่ไม่มีจุดก็ใช้ `(s, t)` ของเฟรมก่อนได้

## 6.2 ทำไมโมเดล "metric" ได้ 54.3 cm: ถูกที่ค่ากลาง ผิดที่ตัวคูณต่อเฟรม

DA-v2 Metric-Indoor ควรให้เมตรโดยตรง — **ตาราง 6.2** (6 ฉาก, ค่าต่อเฟรม):

| | ช่วงข้ามฉาก | ความหมาย |
|---|---|---|
| median(GT / pred) ต่อฉาก | 0.69–0.85 | โมเดลบอกไกลเกินจริง 15–31 % โดยเฉลี่ย (bias ต่อฉาก) |
| ช่วง GT / pred ภายในฉาก | เช่น 0.41–0.86, 0.43–1.35 | เฟรมในห้องเดียวกันผิดได้ตั้งแต่ −59 % ถึง +35 % |
| oracle `t` ใน inverse space | −0.11 … −0.02 (≈ 0) | **ไม่มี shift** — รูปทรงถูกในความหมาย affine |
| AbsRel: ดิบ → scale-only ต่อเฟรม → oracle (s, t) | 0.381 → **0.045** → 0.035 | ตัวคูณเดียวต่อเฟรมกู้ได้ 97 % ของช่องว่าง |
| AbsRel: scale เดียวทั้งฉาก | 0.126 | เหมือน per_scene ของโมเดล relative: ค่ากลางไม่พอ |

ผลรวมในสเปซ 3D คือผิวเดียวกันจากหลายเฟรมถูกวางซ้อนกันหลายระยะ → TSDF เฉลี่ยเป็นก้อนหนา: accuracy 70.3 cm แต่ completeness 38.3 cm (ตาราง 5.1) — ผิวมีครบแต่อยู่ผิดที่
และฉากที่พังที่สุด (45261556 ครัว, 71.1 cm) คือฉากที่รูปทรงของโมเดลดีเป็นอันดับต้น ๆ ใน oracle (4.5 cm) — ยืนยันว่าเป็นเรื่องสเกลล้วน ๆ
เฟรมที่แย่สุดในทุกฉากมีลักษณะเดียวกัน: ผิวเรียบสีเดียวเต็มเฟรม (ตู้ขาว, กระเบื้อง) ที่ไม่มีวัตถุไกล ๆ ให้เทียบ — prior ของโมเดลดันผิวเรียบออกไปไกล

**นัยต่อระบบ:** โมเดล metric ไม่ได้ปลด calibration แต่ลดจาก 2 พารามิเตอร์ต่อเฟรม (s, t) เหลือ **1 (s)** ซึ่งเป็นข้อได้เปรียบจริง:
จุด VIO ไม่กี่จุดต่อเฟรมพอสำหรับ fit scalar เดียวอย่างเสถียร ในขณะที่ fit (s, t) ต้องการจุดกระจายทั้งช่วง depth
อีกทางหนึ่งคือใส่ตัวคูณนั้นไว้ในน้ำหนักโมเดลเลย: fine-tune checkpoint เดียวกันด้วยเฟรม iPad จริง 3,594–19,896 เฟรม
ย้ายแถวนี้ไปที่ 14.6–16.6 cm โดยไม่ต้อง fit อะไรตอนใช้งาน (§5.6) — คำตอบที่ deploy ได้สำหรับเครื่องที่ไม่มีทั้ง LiDAR และจุด VIO ที่เชื่อถือได้

## 6.3 ห้องไหนยาก และยากสำหรับใคร

จัดอันดับฉากตาม Chamfer ของแต่ละแถว (ตาราง 5.2):

| | ง่ายสุด → ยากสุด | ช่วง |
|---|---|---|
| Faro / LiDAR | ห้องนอน 47333774 → ห้องน้ำ 42897743 | 1.2–2.8 / 2.4–4.1 |
| mono + oracle | ครัว 45261556 → ห้องน้ำ | 4.6–10.7 |
| mono + per_scene | นั่งเล่น 47115299 → ห้องนอน 47333774 | 19.9–26.2 |

- **ห้องน้ำยากสำหรับทุก source** (LiDAR +1.3, oracle +6.6 จาก LiDAR) — กระจกเงาให้ depth ปลอมทั้งกับ LiDAR และโมเดล, กระเบื้องมันสะท้อน;
  เป็นฉากเดียวที่ oracle fit ให้ `s ≤ 0` ในบางเฟรม (เฟรมกระจกทั้งบาน) ถ้าตลาดเป้าหมายคือ renovation ห้องน้ำ ตัวเลขเฉลี่ยของเปเปอร์นี้ optimistic
- **ห้องนอนมาตรฐาน 47333774 ง่ายที่สุดสำหรับ LiDAR แต่ยากอันดับ 2 สำหรับ mono** (oracle 8.1) — ห้องเล็กที่เดินถ่ายใกล้ผนัง/เตียง ทำให้เฟรมส่วนใหญ่เป็นระยะ 1–2 m ที่ผนังเรียบ
  ไม่มี cue; ห้องที่มี "ของเยอะ" (ครัว 45261556: ตู้ 10 ใบ, นั่งเล่น: โต๊ะ 4 โซฟา 2) กลับง่ายสำหรับ mono — โมเดลชอบวัตถุที่รู้ขนาด
- ลำดับความยากของ mono ไม่ตรงกับ LiDAR ⇒ **ประเมิน "ฉากยาก" ต้องทำต่อ source** ใช้ประสบการณ์จาก LiDAR มาเดาว่า mono จะพังที่ไหนไม่ได้

## 6.4 สิ่งที่เห็นเฉพาะใน 3D: mono ขัดแย้งกับตัวเองข้ามมุมมอง

Exp3 ให้หลักฐานที่ตัวชี้วัด 2D ไม่แสดง: เมื่อลดเฟรมจาก 391 → 20 (stride 20) **accuracy ของ mono+oracle ดีขึ้น 7.1 → 5.1 cm** ทั้งที่ AbsRel 2D คงที่ 0.040
ส่วน GT ไม่เปลี่ยน (1.3 → 1.3) แปลว่าแม้แต่ละเฟรมของ mono ถูก scale อย่างสมบูรณ์แล้ว รูปทรงของผิวเดียวกันจากคนละมุมยัง**ไม่ตรงกัน** ระดับ ~2 cm
และการ fuse เฟรมมากขึ้นทำให้ผิวหนาขึ้น ไม่ใช่แม่นขึ้น — คุณสมบัติ multi-view consistency ที่ LiDAR มีแต่โมเดล single-image ไม่มี
นี่คือส่วนของช่องว่าง oracle→LiDAR (2.3 cm) ที่ scale alignment แก้ไม่ได้ และเป็นเหตุผลที่งานอย่าง SimpleRecon ใช้ cost volume หลายภาพ (§2.2) แถว sparse ก็รับมรดกนี้: ช่องว่างที่เหลือถึง LiDAR (2.9 cm) คือเทอมรูปทรงนี้

## 6.5 ข้อสรุปสำหรับการออกแบบระบบ

| สิ่งที่คิดก่อนทำ | สิ่งที่ข้อมูลบอก |
|---|---|
| ปัญหาของ mono คือรูปทรงหยาบ | รูปทรงห่าง LiDAR 2.3 cm; scale ห่าง 18 cm |
| calibrate ครั้งเดียวต่อห้องพอ | ไม่พอ — 22.9 cm ทุกห้อง; scale ขึ้นกับมุมมอง |
| โมเดล metric ปลดปัญหา scale | ไม่ — แต่ลดเหลือ 1 พารามิเตอร์ต่อเฟรม |
| โมเดล metric แก้ไม่ได้ถ้าไม่มี laser scanner | แก้ได้ — fine-tune ด้วยครูที่เป็น LiDAR ในมือถือก็พอ (§5.6) |
| จุด sparse ไม่กี่จุดแก้ dense map ไม่ได้ | ได้ — 200 จุด/เฟรม → ห่าง oracle 0.6 cm |
| confidence map ของ LiDAR = ความแม่นฟรี | ไม่ — mask/weight ไม่เปลี่ยนอะไร (Exp5) |
| โมเดลใหญ่กว่า = ห้องแม่นกว่า | +1.0 cm จาก S→L เทียบกับ +17.6 cm จาก scale |
| เฟรมเยอะ = แม่นกว่า | เฟรมเยอะ = ครบกว่า; accuracy ของ mono ดีขึ้นเมื่อเฟรมน้อยลง |
| ฉากยากของ LiDAR = ฉากยากของ mono | ไม่ตรงกัน (ห้องนอนเรียบยากสำหรับ mono, ง่ายสำหรับ LiDAR) |
