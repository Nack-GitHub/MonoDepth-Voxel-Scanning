\section{Conclusion}
We asked whether transfer learning with depth from a phone's own LiDAR really makes a metric monocular model better than
its pretrained self, measured against the laser scanner that ARKitScenes provides as ground truth, and answered it
through a room-reconstruction pipeline (per-frame depth $\rightarrow$ scale alignment $\rightarrow$ TSDF $\rightarrow$
mesh) in which \textbf{the depth source is the single variable switched from config}. The numbers say:
\begin{enumerate}
\item \textbf{Yes, in every room we can measure.} Fine-tuning only the head of DA-v2 Metric-Indoor with iPad LiDAR
labels on 24 rooms (R3) lowers Chamfer from \SI{\rsMETRICCM}{cm} to \SI{\rsFTLIDARALLCM}{cm} on all six held-out rooms
(\fscore{} \rsMETRICF{} $\rightarrow$ \rsFTLIDARALLF; AbsRel against Faro \rsMETRICSIXABSREL{} $\rightarrow$
\rsFTLIDARALLABSREL), and per-frame AbsRel from \rsVMETRICABSREL{} to \rsVFTALLABSREL{} on \rsVN{} further
Validation-fold rooms (better in \rsVWINS/\rsVN)---with no calibration and no sensor at run time.
\item \textbf{The teacher does not need to be a laser scanner.} Faro, LiDAR on the same rooms and LiDAR on more rooms
give \SI{\rsFTFAROCM}{cm} / \SI{\rsFTLIDARCM}{cm} / \SI{\rsFTLIDARALLCM}{cm}, within the across-room spread, so the
training data for devices without a depth sensor can be collected by devices that have one. Knowing the camera is no
substitute: Depth Pro with the true focal length reaches \SI{\rsDEPTHPROCM}{cm}.
\item \textbf{It is not yet a sensor.} Through the same pipeline iPad LiDAR costs \SI{\rsLIDARCM}{cm}, monocular depth
with the correct scale per frame \SI{\rsORACLECM}{cm}, and a per-frame fit on 200 sparse metric points---what a phone's
tracker provides---\SI{\rsSPARSECM}{cm}. R3 (recall@\SI{10}{cm} \rsFTLIDARALLRten) is still short of the ``rough overview'' tier
(0.9), and further from furniture placement.
\item \textbf{The remaining error is a scale that swings per view, not shape}: one calibration per scene gives
\SI{\rsSCENECM \pm \rsSCENESD}{cm} in every room; the model's per-frame scale varies severalfold within a scan,
uncorrelated with time but correlated with what is in the frame. Fine-tuning removes the domain bias of that scale;
the per-frame factor still needs metric data at run time.
\item \textbf{Secondary costs are small}: the pipeline itself loses \SI{2.1 \pm 0.5}{cm} at \SI{4}{cm} voxels; DA-v2
Small costs \SI{1.0}{cm} for a $6\times$ speed-up; $\geq 0.8$~fps suffices for a complete room; LiDAR confidence
weighting changes nothing.
\end{enumerate}
The systems result: separating \code{DepthSource} and \code{ScaleAligner} into interfaces made all experiments pure YAML
and made each fine-tuned checkpoint a new row in an existing table; the orchestrator was edited once in the whole project
(two lines for confidence weights). The same code, behind a small upload/queue/view service and a loader for the app's
capture folder, is the product's backend. Next steps: a controlled teacher comparison on identical frames, a larger
validation set, fine-tuning data from more phone cameras, and combining the fine-tuned model with real ARKit/ARCore
feature points to fix the per-frame scale it leaves.
