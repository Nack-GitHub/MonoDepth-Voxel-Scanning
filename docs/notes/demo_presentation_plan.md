> ถ้าตัวเลขในเปเปอร์เปลี่ยน ให้แก้ตารางในหัวข้อ 5 ของไฟล์นี้ด้วย

## 0. สรุปสั้นก่อนอ่าน

- **ข้อความหลักที่ demo ต้องทำให้กรรมการ "เห็นด้วยตา"** มีสามข้อ:
  1. โมเดล pretrained (DA-v2 Metric-Indoor) วางห้องผิดไป **54.3 cm** เพราะทายไกลเกิน 1.18–1.45 เท่า
  2. fine-tune ด้วย LiDAR ของ iPad เอง (FT-LiDAR-24) ลดเหลือ **15.7 cm** (ดีขึ้น 3.5 เท่า ดีกว่าในทั้ง 6 ห้อง) โดยตอนใช้งานไม่ต้องมี sensor หรือ calibration
  3. แต่ยังห่างจาก iPad LiDAR (**3.0 cm**) เพราะ scale ยังแกว่งตามมุมมองจากเฟรมหนึ่งไปอีกเฟรม ซึ่ง fine-tune แก้ไม่ได้
- **ภาพที่ช่วยได้มากที่สุด**: mesh 3 ก้อนวางเทียบกัน (pretrained | FT-LiDAR-24 | LiDAR) ที่หมุนกล้องไปพร้อมกัน และระบายสีตาม error เทียบกับ Faro
- **front-end ทำแบบนั้นได้แล้ว** (P0 + P1 ตาม `SPEC.md` เสร็จเมื่อ 2026-09-30 บน branch `feat/web-demo`): เทียบ 3 ช่องด้วยกล้องเดียว, สี error เทียบ Faro, Faro overlay, แผง metric พร้อม badge, gallery ของผล Exp1/Exp6 และงานไม่หายเมื่อ restart server (รายละเอียดอยู่ในหัวข้อ 1) สิ่งที่ยังต้องทำบนเครื่อง demo คือซ้อมกับข้อมูลจริง เพราะเครื่องที่พัฒนาไม่มี mesh ของ sweep และไม่มี ARKitScenes ของห้องทดสอบ
- **อย่ารันโมเดล mono สดบนเวที** เพราะ FT-LiDAR-24 ใช้เวลา 3–7 นาทีต่อห้อง (ห้อง 47429736 ใช้ 438 s ตาม `metrics.json`) ให้รันไว้ก่อน แล้วรันสดเฉพาะงาน LiDAR ที่เสร็จในไม่กี่วินาที เพื่อแสดงว่าระบบทำงานได้จริง

## 1. Front-end: ตอนนี้มีอะไรแล้ว และต้องเพิ่มอะไร

### 1.3 สิ่งที่ทำแล้ว (P0 + P1) และสิ่งที่เหลือ (P2)

ทุกข้อด้านล่างแก้แค่ใน `src/roomscan_web/`, `scripts/` และ `tests/test_web.py` **ไม่แตะ `pipeline.py`** ตามกฎใน `CLAUDE.md`
รายละเอียดของ endpoint และไฟล์อยู่ใน `docs/architecture/README.md` §7.1 ส่วนข้อกำหนดอยู่ใน `SPEC.md`

#### P0: เสร็จแล้ว

1. **Preset `ft_lidar_24`** (G1, G9): preset ย้ายไปอยู่ฝั่ง server (`presets.py`, `GET /presets`) ชื่อใน dropdown ตรงกับเปเปอร์ และ `mono_sparse` ใช้ `depth_anything_v2_large` พร้อมคำว่า "upper bound" เสมอ
   - weights อยู่ใน HF repo แบบ private (`NackPanupong/roomscan-dav2-metric-large-ft-lidar-all`) เครื่องที่ใช้ demo ต้อง `huggingface-cli login` แล้วโหลด weights มาเก็บไว้ก่อน วันจริงให้ตั้ง `HF_HUB_OFFLINE=1` เพื่อไม่ให้ไปพึ่งเน็ต
2. **เก็บงานไว้ถาวร** (G2): ทุกงานมี `job.json` ข้าง `metrics.json` ซึ่งเก็บ preset ไว้ด้วย ป้ายชื่อจึงถูกหลัง restart งานที่ค้างอยู่ตอน server ปิดจะขึ้นว่า `failed: interrupted by server restart` และ**ไม่ถูกรันซ้ำเอง** (กันไม่ให้งาน mono 7 นาทีเริ่มเองตอนเปิดเครื่องบนเวที)
3. **โหมดเปรียบเทียบ 1–3 mesh** (G3): ติ๊ก "compare" ได้สูงสุด 3 รายการ ทุกช่องใช้กล้องเดียวกัน กล้องถูกตั้งครั้งเดียวจาก Faro reference (ถ้าไม่มีใช้ช่อง LiDAR) จึงเห็นว่า mesh ของ pretrained ใหญ่เกินห้องจริง ใต้แต่ละช่องมีชื่อ, Chamfer และป้ายที่มา ("paper run" หรือ "demo run (stride N, no GT mask)") ถ้าเลือกคนละห้องจะขึ้นแถบ "different rooms — not comparable"
4. **ระบายสีตาม error** (G4): `GET /scans/{id}/error.ply` และ `GET /gallery/.../error.ply` ใช้ turbo 0–10 cm เท่ากับ Fig. exp6 มีปุ่ม "Color: real / error" กับ legend ถ้าไม่มี reference ปุ่มจะถูกปิดพร้อม tooltip "no Faro reference"
5. **แผง metric แบบเต็ม** (G5): Chamfer, Accuracy, Completeness, F@5, Recall@2/5/10, เวลา depth / fusion / total และ badge Overview (R@10), Furniture (R@5), Renovation (R@2) ตามเกณฑ์ ≥ 0.9 = ✓, 0.75–0.9 = ~, < 0.75 = ✗ พร้อมหมายเหตุว่าเกณฑ์เป็นตัวอย่างประกอบ แผงนี้แสดงของรายการที่คลิกหรือช่องที่เมาส์ชี้อยู่
6. **three.js ในเครื่อง** (G7): หน้าเว็บถูกแตกเป็น `app.css` + ES modules ที่เสิร์ฟจาก `/static` และ three.js 0.160.0 อยู่ใน `static/vendor/three/` แล้ว หน้าเว็บจึงไม่มี request ออกนอกเครื่อง

#### P1: เสร็จแล้ว

7. **แกลเลอรีผลการทดลอง** (G6): แท็บ Gallery เป็นตาราง source × ห้อง แสดง Chamfer ทุกช่อง กดช่องเพื่อเลือกเทียบ (นับรวมกับงานบนเว็บ สูงสุด 3) และกดเลขห้องเพื่อเทียบ pretrained / FT-LiDAR-24 / iPad LiDAR ของห้องนั้นในคลิกเดียว ใช้ตอบเมื่อกรรมการขอดูห้องอื่น
   - แกลเลอรีแสดงเฉพาะ run ที่ยังมี `mesh.ply` จึงใช้ได้บนเครื่องที่รัน sweep เท่านั้น และต้องมี `data/arkitscenes` ของห้องนั้นจึงจะมีสี error กับ overlay
8. **ตัวจับเวลาและสถานะ** (G8): งานที่กำลังรันแสดง `running 01:23` โดยนับจากเวลาของ **server** (`elapsed_s`) ไม่ใช่เวลาที่กดอัปโหลดฝั่ง client เมื่อ reload หน้าจึงยังนับถูก และแสดงเวลาที่คาดไว้จาก preset × จำนวนเฟรม
9. **ตั้ง Z-up อัตโนมัติ** (G10): `export_capture.py` เขียน `meta.json` (`scene`, `up: "z"`, `stride`) และ viewer ตั้งค่าตามนั้น capture ที่ export ไว้ก่อนวันที่ 2026-09-30 ไม่มีไฟล์นี้ ต้อง `make capture-zip` ใหม่
10. **Faro overlay**: `GET /scans/{id}/reference.ply` ส่งสำเนา Faro ที่ลดจำนวนสามเหลี่ยมแล้ว หน้าเว็บวาดเฉพาะเส้นขอบมุม (ผนังชนผนัง ผนังชนพื้น ขอบเฟอร์นิเจอร์) และวาดทับ mesh เสมอ จึงเห็นห้องจริงอยู่ข้างใน mesh ของ pretrained ที่พองออก

#### P2: มีแล้วดี ถ้ามีเวลาเหลือ

11. **แท็บ "Scale รายเฟรม"** (G11): ใช้ไฟล์ `paper/analysis/<scene>_scale_drift_da_{metric,ft_lidar_all,large}.json` ที่มีอยู่แล้ว (field `gt_over_pred_median`, `gt_median`, `timestamp`) วาดกราฟ 2 รูป

    - เสิร์ฟ JSON ผ่าน endpoint แบบอ่านอย่างเดียว หรือ copy ไฟล์ไปไว้ใน static ก็ได้

13. **เครื่องมือวัดระยะ** (G12): คลิก 2 จุดบน mesh ด้วย Raycaster แล้วแสดงระยะเป็น cm ใช้วัดความกว้างห้องบน mesh ของ pretrained เทียบกับ FT และ LiDAR ได้ (เช่น ผนังถึงผนัง 6.6 m เทียบกับ ~8 m)

> **ถ้ามีเวลาแค่ 1–2 วัน** ให้ทำ P0 ข้อ 1, 2, 5, 6 ก่อน ส่วนข้อ 3 และ 4 ให้ใช้ภาพจาก Fig. exp6 ในสไลด์แทนไปก่อน
> **ถ้ามี 3–5 วัน** ทำ P0 ให้ครบ แล้วเพิ่มข้อ 7 กับข้อ 10
> ทุกข้อต้องมี test ใน `tests/test_web.py` (ใช้ synthetic scene และต้องไม่ใช้ torch ตามกฎของ `make test`)

### 1.4 สิ่งที่ **ไม่ควร** ทำหรือพูดใน demo

- อย่าอ้างว่านี่คือแอปบน Android หรือทำงานแบบ real-time บนมือถือ เพราะเปเปอร์ระบุว่าอยู่นอกขอบเขต ระบบนี้เป็น offline pipeline ที่ใช้เวลาประมาณ 3.6 เท่าของความยาววิดีโอบน laptop เมื่อใช้ DA-v2 Large
- อย่าโชว์ผลของ synthetic scene ว่าเป็นผลการทดลอง (กฎใน `CLAUDE.md`)
- อย่าใช้ห้อง 42444474 เป็นห้องหลักของ demo เพราะเป็นห้องที่ใช้ตอนพัฒนา (ไม่ได้ held-out) ให้ใช้ห้องในหัวข้อ 2.2 แทน
- ถ้าโชว์ sparse points ต้องพูดทุกครั้งว่าเป็น **upper bound** เพราะสุ่มจาก LiDAR ไม่ใช่จุด VIO จริง

## 4. การเตรียมตอบคำถาม

คำตอบด้านล่างเป็นแนวทาง ควรพูดด้วยสำนวนของตัวเอง ทุกตัวเลขมาจาก main_short

### 4.1 ที่มาและความสำคัญ

**Q: ทำไมไม่ใช้ LiDAR ไปเลย ในเมื่อแม่นกว่ามาก**
A: เพราะเครื่องที่มี LiDAR เป็นส่วนน้อย มีเฉพาะ iPhone/iPad Pro ส่วน iPhone รุ่นธรรมดาและ Android เกือบทั้งหมดไม่มี งานนี้ไม่ได้บอกว่าให้เลิกใช้ LiDAR แต่ใช้ LiDAR ของเครื่อง Pro มาสอนเครื่องที่ไม่มี LiDAR

**Q: contribution ของงานนี้คืออะไร โมเดลก็ไม่ได้ออกแบบใหม่**
A: มีสามข้อ (1) แสดงว่า label จาก LiDAR ของเครื่องเอง ซึ่งแอปเก็บได้ระหว่างการใช้งานปกติ พอจะลด error ได้ 3.5 เท่าโดยไม่ต้องใช้ laser scanner ในการสร้าง weights (2) วัดผลใน pipeline ที่ depth source เป็นตัวแปรเดียว จึงตอบเป็นเซนติเมตรต่อห้องได้ ซึ่ง benchmark แบบรายภาพตอบไม่ได้ (3) ชี้ว่า error ที่เหลือคือ scale ที่แกว่งตามมุมมอง ซึ่งบอกว่าควรลงทุนอะไรต่อ

**Q: ทำไมไม่เทียบกับ Atlas / NeuralRecon / SimpleRecon**
A: ระบบเหล่านั้นออกแบบ pipeline ทั้งหมดรอบโมเดลของตัวเอง และใช้หลายเฟรมต่อการทาย ตัวเลขจึงเทียบกันตรง ๆ ไม่ได้ งานนี้ตั้งใจตรึง pipeline ไว้แล้วเปลี่ยนเฉพาะ depth source เพื่อแยกผลของ depth ออกมา ระบบเหล่านั้นระบุไว้ว่าอยู่นอกขอบเขต

### 4.2 วิธีการ

**Q: ทำไม train แค่ DPT head แล้ว freeze encoder**
A: ทำตามแนวของ DINOv2 ที่ train เฉพาะ decoder สำหรับ depth ข้อดีคือใช้หน่วยความจำน้อยจนพอกับ GPU 8 GB และเสี่ยง overfit กับ 24 ห้องน้อยกว่า ผลก็สอดคล้องกัน คือ "รูปร่าง" ของ depth แทบไม่เปลี่ยน (AbsRel แบบ per-frame oracle 0.035 เทียบกับ 0.042) สิ่งที่ head เรียนไปคือ scale การ fine-tune ทั้งเครือข่ายเป็นงานต่อไป

**Q: ทำไมใช้ SiLog loss**
A: เป็น loss มาตรฐานของ metric depth ส่วน variance ของ log-difference วัดรูปร่าง ส่วน 0.15 × mean² วัด scale รวม จึงลงโทษทั้งสองอย่าง

**Q: ทำไมไม่ zoom ตอน augment**
A: การขยายภาพทำให้วัตถุดูใหญ่ขึ้น ซึ่งเท่ากับสอนโมเดลว่าของอยู่ใกล้กว่าความจริง จึงใช้แค่ crop, flip และ colour jitter

**Q: ground truth คืออะไร ทำไมไม่ใช้ LiDAR เป็น GT**
A: GT คือ depth จาก Faro Focus S70 ที่ dataset แจกมา ส่วน reference mesh ได้จากการ fuse Faro ที่ voxel 1 cm LiDAR ไม่เคยถูกใช้เป็น GT เพราะมันคือหนึ่งใน source ที่ถูกวัด

**Q: ใช้ pose จาก ARKit ทุกแถว ไม่เป็นการโกงหรือ**
A: เป็นการตั้งใจตัด pose error ออก เพื่อให้ความต่างระหว่างแถวมาจาก depth อย่างเดียว ระบบจริงบนมือถือจะมี pose drift เพิ่มเข้ามา ซึ่งเขียนไว้ในข้อจำกัดแล้ว ตัวเลขจึงเป็นกรณีที่ดีที่สุดในแง่ pose

**Q: Chamfer, F-score, AbsRel, within-1.25× คืออะไร**
A: Chamfer คือระยะเฉลี่ยจากผิวหนึ่งไปหาจุดที่ใกล้ที่สุดบนอีกผิว คิดทั้งสองทาง F@5 cm รวมสัดส่วนของ mesh ที่อยู่ภายใน 5 cm ของ reference (precision) เข้ากับสัดส่วนของ reference ที่ถูกสร้างภายใน 5 cm (recall) AbsRel คือ error สัมพัทธ์เฉลี่ยรายพิกเซล |pred − gt| / gt within-1.25× คือสัดส่วนพิกเซลที่ค่าที่ทายอยู่ภายใน 1.25 เท่าของค่าจริง

**Q: ทำไม voxel 4 cm**
A: Exp2 แสดงว่าด้วย Faro depth ที่ 2 / 4 / 8 cm ได้ Chamfer 1.2 / 2.1 / 2.8 cm ที่ 4 cm ความสูญเสียจากการแบ่ง voxel ของ pipeline เองยังเล็กกว่า error ของทุก source ที่ไม่ใช่ Faro มาก และเข้ากับความละเอียดของ LiDAR 256×192

### 4.3 ข้อมูล สถิติ และความถูกต้องของการทดลอง (คำถามที่หนักที่สุด)

**Q: 6 ห้องน้อยเกินไปไหม**
A: ใช่ และระบุไว้ในข้อจำกัด ด้วย Wilcoxon แบบ exact บน 6 ห้อง p ที่เล็กที่สุดที่เป็นไปได้คือ 2/64 ≈ 0.031 ซึ่งจะได้ก็ต่อเมื่อชนะครบทั้ง 6 ห้อง และ FT-LiDAR-24 ก็ชนะครบ ด้วยเหตุนี้จึงเพิ่ม Exp7 อีก 20 ห้องที่ไม่ได้ใช้ตัดสินอะไรเลย ผลคือ AbsRel ดีขึ้น 19/20 ห้อง p = 3.8×10⁻⁶ แต่ Exp7 เป็นการวัดรายเฟรม ไม่มี 3D เพราะการสร้าง reference mesh ใช้ดิสก์มาก

**Q: เลือก checkpoint ด้วย Faro แล้วจะบอกว่า "ไม่ต้องใช้ laser" ได้อย่างไร**
A: weights เรียนจาก LiDAR ล้วน ส่วน Faro ใช้เฉพาะเลือก checkpoint บน 3 ห้อง validation ซึ่งไม่ใช่ห้องทดสอบ เปเปอร์จึงเขียนว่า "laser-scanner depth only chooses the checkpoint, on three rooms" และเสนองานต่อไปว่าให้เลือก checkpoint ด้วย LiDAR ด้วย เพื่อให้ไม่มีขั้นไหนต้องใช้ laser

**Q: มี data leakage ระหว่าง train กับ test ไหม**
A: แยกตาม visit คือ session ที่ถ่ายบ้านหลังเดียวกัน ไม่ใช่แยกตามวิดีโอ ห้องทดสอบ 6 ห้องและทุก visit ของห้องเหล่านั้นไม่ถูกใช้ train, validate หรือเลือก checkpoint (`configs/training/splits.yaml`) และ Exp7 ก็ตัดทุก visit ที่ซ้ำกับชุดใดก็ตามออก

**Q: เลือกการเปรียบเทียบหลักหลังเห็นผลแล้ว ไม่ใช่ HARKing หรือ**
A: ยอมรับว่าการเปรียบเทียบหลักถูกกำหนดหลังจาก Exp6 รันแล้ว และเปิดเผยไว้ในข้อจำกัด (ADR-014) เพื่อไม่ให้ข้อสรุปยืนอยู่บนห้องที่เห็นผลแล้วเท่านั้น จึงเพิ่ม 20 ห้องของ Exp7 ที่เลือกด้วย seed คงที่ก่อนรัน และผลก็ยืนยันไปในทางเดียวกัน

**Q: ห้อง 42444474 ใช้ตอนพัฒนา ไม่ลำเอียงหรือ**
A: ใช่ จึงระบุไว้และให้ผลรายห้อง ถ้าตัดห้องนี้ออก FT ก็ยังดีกว่า pretrained ในห้องที่เหลือทั้ง 5 ห้อง (ตาราง perroom)

**Q: ทำไม within-1.25× ถึงดีขึ้นแค่ 5/6 ห้อง**
A: ห้อง 47115299 ลดลงจาก 0.74 เป็น 0.60 ห้องนี้เป็นห้องนั่งเล่นขนาดใหญ่ที่ scale ของ pretrained แกว่งกว้างมาก (0.43–1.35) และรายงานไว้ตรง ๆ ส่วน Chamfer, F@5 และ AbsRel ดีขึ้นครบ 6/6

**Q: ห้องไหนใน Exp7 ที่ FT ไม่ชนะ**
A: ห้อง 48018730 AbsRel แทบไม่เปลี่ยน (0.275 → 0.281) เป็นห้องที่ pretrained ทำได้ค่อนข้างดีอยู่แล้ว (AbsRel ต่ำเป็นอันดับที่ 5 จาก 20)

### 4.4 การตีความผล

**Q: 15.7 cm ยังแย่กว่า sparse points (6.0 cm) ตั้งเยอะ แล้วจะใช้ FT ทำไม**
A: sparse points ต้องมีจุด metric ตอนใช้งานทุกเฟรม และตัวเลข 6.0 cm เป็น upper bound เพราะสุ่มจาก LiDAR ที่สะอาดกว่าจุด VIO จริง ส่วน FT ใช้แค่ภาพสีโดยไม่ต้องใช้อะไรเพิ่ม ทั้งสองจึงไม่ได้แข่งกัน แต่ใช้ร่วมกันได้ ตาราง scale แสดงว่าถ้า FT ได้ scale ที่ถูกทุกเฟรม AbsRel จะเหลือ 0.051 นี่คืองานต่อไปอันดับแรก

**Q: FT ต่างจากการ calibrate ครั้งเดียวต่อห้องอย่างไร**
A: FT ที่ไม่มีตัวช่วยใด ๆ ได้ AbsRel 0.134 ใกล้กับ pretrained ที่ได้ scale และ offset ต่อห้องซึ่ง fit บน Faro GT (0.127) แปลว่าสิ่งที่การ calibrate ให้ ย้ายเข้าไปอยู่ใน weights แล้ว และไม่ต้องมี GT หรือขั้นตอน calibrate ตอนใช้งาน

**Q: ทำไม Faro teacher ไม่ดีกว่า LiDAR teacher**
A: error ของ LiDAR เมื่อเป็น label (AbsRel 0.018) เล็กกว่า error ที่ยังเหลือในโมเดล (0.134) ประมาณ 10 เท่า ความแม่นที่เพิ่มขึ้นจาก label จึงไม่ใช่คอขวด แต่ต้องระวังว่าด้วย 6 ห้อง test จะเห็นความต่างก็ต่อเมื่อต่างครบทุกห้อง ความต่าง 1–2 cm จึงยังตัดทิ้งไม่ได้ และ FT-Faro-10 กับ FT-LiDAR-10 ยังเห็นจำนวน view ไม่เท่ากันด้วย (LiDAR มากกว่าประมาณ 2.4 เท่า)

**Q: 24 ห้องไม่ดีกว่า 10 ห้อง แปลว่าข้อมูลมากไม่ช่วยหรือ**
A: ใน 6 ห้องทดสอบยังไม่เห็นความต่างที่มีนัยสำคัญ (FT-LiDAR-24 ดีกว่า FT-LiDAR-10 ใน 5/6 ห้อง, p = 0.44) และข้อค้นพบใน objective 4 ชี้ว่า error ที่เหลือมาจากความกำกวมของภาพเอง ซึ่งการเพิ่ม label อย่างเดียวอาจแก้ไม่ได้

**Q: ทำไม Depth Pro แย่มาก (155 cm) ทั้งที่เป็นโมเดลใหม่**
A: ภาพ 640×480 ในบ้านแบบนี้ไม่ใช่แบบที่มันถนัด เมื่อให้มันเดา FOV เอง มันเดาได้ 48.0–48.7° แต่ของจริงคือ 61.6° และแม้ตัด scale รายเฟรมออกแล้ว AbsRel ยังเป็น 0.24–0.54 เทียบกับ 0.04–0.13 ของ DA-v2 ข้อสรุปจึงใช้ได้กับ implementation นี้บนข้อมูลนี้ ไม่ได้ครอบคลุมโมเดลตระกูล camera-aware ทั้งหมด (ไม่ได้ทดสอบ Metric3D หรือ UniDepth)

**Q: "scale แกว่งตามมุมมอง ไม่ใช่ตามเวลา" หมายความว่าอะไร และรู้ได้อย่างไร**
A: ถ้าเป็น drift ตามเวลา scale ควรสัมพันธ์กับเวลาในทิศเดียวกันทุกห้อง แต่ผลที่ได้คือ −0.40 ถึง +0.30 บวก 3 ห้อง ลบ 3 ห้อง ในขณะที่ความสัมพันธ์กับความลึกของเฟรมเป็นลบ**ทุกห้อง** (−0.75 ถึง −0.27) คำอธิบายที่เป็นไปได้คือภาพระยะใกล้ เช่นโต๊ะหรือผนังเปล่า ไม่มีเบาะแสบอกขนาดจริง โมเดลจึงเดาไปที่ระยะในห้องทั่วไป ซึ่งเป็นการตีความ ไม่ใช่การพิสูจน์

**Q: ทำไมห้องน้ำที่มีกระจกถึงแย่ที่สุด**
A: กระจกกับกระเบื้องมันวาวสะท้อนภาพ ทำให้ทั้ง depth จากภาพและ LiDAR สับสน สำหรับ source ที่ scale ถูกแล้วห้องนี้ยากที่สุด (Faro 2.8, LiDAR 4.1, oracle 7.5, sparse 9.1 cm) เป็นข้อจำกัดที่รู้กันดีของ depth sensing

### 4.5 ธุรกิจและการใช้งานจริง

**Q: เอาไปใช้งานจริงได้เลยไหม**
A: ยังไม่ได้สำหรับงานที่ต้องการความแม่น ตามเกณฑ์ในเปเปอร์ FT ยังไม่ผ่านแม้แต่ overview (recall@10 cm = 0.51 จากเกณฑ์ 0.9) ส่วน iPad LiDAR ผ่าน overview และ furniture ที่ใช้ได้เลยคือแนวทางการเก็บ label และลำดับการลงทุน คือ scale รายเฟรมก่อน แล้ว fine-tune แล้วค่อยเรื่องขนาดโมเดล

**Q: เกณฑ์ 2 / 5 / 10 cm มาจากไหน**
A: เป็นตัวอย่างประกอบที่ผู้วิจัยตั้งขึ้นเพื่อเชื่อมตัวเลขเข้ากับ use case ไม่ใช่มาตรฐานอุตสาหกรรม ซึ่งเขียนไว้ในข้อจำกัดแล้ว

**Q: เก็บ LiDAR จากผู้ใช้ Pro ได้จริงหรือ แล้วเรื่องความเป็นส่วนตัวล่ะ**
A: ในทางเทคนิค ARKit ให้ภาพสี LiDAR depth และ pose มาพร้อมกันอยู่แล้ว แต่การเก็บจริงต้องขอความยินยอม (consent) และทำให้ข้อมูลไม่ระบุตัวตน เพราะภาพในบ้านเป็นข้อมูลส่วนบุคคล (มี PDPA/GDPR เกี่ยวข้อง) ประเด็นนี้ไม่ได้อยู่ในขอบเขตของงาน แต่ต้องคิดก่อนนำไปใช้

**Q: ใช้บน Android ได้ไหม**
A: ยังไม่ได้ทดสอบ ข้อมูลทั้งหมดมาจาก iPad รุ่นเดียว กล้องที่ต่างไป (focal length, ISP) อาจทำให้ scale ที่เรียนไว้เพี้ยน การ train และประเมินบนกล้องหลายรุ่นรวมถึง Android เป็นงานต่อไปข้อ 3

**Q: เร็วแค่ไหน ใช้บนมือถือได้ไหม**
A: เป็น offline pipeline บน laptop ด้วย DA-v2 Large ใช้เวลาประมาณ 3.6 เท่าของความยาววิดีโอ ถ้าใช้ Small จะเหลือ 0.6 เท่า (เร็วกว่า 6.4 เท่า แต่แย่ลง 1.0 cm) fusion ใช้ไม่ถึง 3% ของเวลา การทำ real-time บนเครื่องอยู่นอกขอบเขต

**Q: ต้นทุนการ train**
A: 12,000 steps ประมาณ 2 ชั่วโมงบน RTX 3070 Ti 8 GB เพราะ train เฉพาะ head

### 4.6 คำถามเกี่ยวกับ demo หรือระบบ

**Q: ตัวเลขบนหน้าเว็บไม่ตรงกับในตาราง**
A: เว็บรันด้วย stride 5 และไม่ได้ mask ตาม GT เหมือน sweep ของการทดลอง ตัวเลขอย่างเป็นทางการคือในตาราง ส่วน demo แสดงว่าระบบเดียวกันรันกับไฟล์ที่อัปโหลดได้ **(ตรวจก่อนว่าความต่างเล็กจริง)**

**Q: ระบบรองรับ depth source ใหม่อย่างไร**
A: เพิ่มไฟล์ใหม่ 1 ไฟล์ และเพิ่ม 1 บรรทัดใน registry แล้วเลือกผ่าน config ได้ โดยไม่ต้องแก้ pipeline (ตัวอย่าง: FT ทั้งสามตัวเป็นแค่บรรทัดใน `models/__init__.py` ที่ชี้ไปยัง HF repo)

**Q: ทำซ้ำผลได้ไหม**
A: ทุก run มี `config.yaml` และ `metrics.json` commit ไว้ใน `experiments/results/` มีคำสั่ง `make sweep-exp*` และ `make eval-exp7` และแบ่งข้อมูลด้วย seed คงที่ ส่วน weights เก็บไว้ใน HF Hub แบบ private
